# 🔦 Spotlight Feature Tour (gold ring + dim + coach card) Pattern

**Status**: Level 2 (Proven on a staging site with a real iPhone, desktop Chrome and a browser-test pass; not yet in production, promote after the first prod weeks)
**Source**: ONDW food-delivery PWA, multi-cafe checkout tour (sanitised, brand-neutral) | **Framework**: plain JS + inline CSS, server gate in Laravel/Blade (the JS/CSS has no framework dependency)
**Date Added**: Oct 24, 2026 | **Cost to build it twice**: about 8 versions of polish. This file is so the next one takes one.

## What it is
A "feature onboarding" that walks a user through ONE real flow on the real pages: the target element gets a gold ring, the rest of the screen is dimmed, a small coach card sits next to the ring with a short sentence. Not a slideshow: the user taps the real buttons and the tour moves on by itself. Ends with Retry / Done. Shown once per account, replayable from Profile.

## Anatomy (three fixed layers + one card)
| Layer | Job |
|---|---|
| `.tr-spot` | the ring: `position:fixed`, size/position from CSS vars (`--x --y --w --h --r`), gold `box-shadow` ring plus a huge `0 0 0 999px rgba(dim)` shadow = the dim with a hole. Animate left/top/width/height with a 320 ms ease-out so the ring GLIDES when the target moves. `pointer-events:none` |
| `.tr-catch` | blocks every tap except the ringed element: `clip-path: polygon(evenodd, outer rect, hole rect)` (hole = ring rect). On steps where the target must receive the tap the hole lets it through |
| `.tr-blur` (optional, ONE step only) | `backdrop-filter: blur(2px)` clipped with the same hole, `pointer-events:none`. Use on the closing step only: on earlier steps the user must see where they are |
| `.tr-card` | the coach card, z-index above the rest: progress bars, kicker ("Step 3 of 6"), title, one sentence, 1-2 buttons |

## Rules that came from real mistakes (read before building)
1. **Never use `scrollIntoView` or `window.scrollBy` in a tour.** `scrollIntoView` scrolls EVERY scrollable ancestor. In an app shell where `html/body` are `overflow:hidden` and a `<main>` is the only scroller (common in iOS PWAs), the locked document can still be scrolled programmatically by about the toolbar height, content shifts ~48px against the `position:fixed` ring and the ring sits visibly off. Fix: find the real scroller (`scrollerOf(el)` = nearest ancestor with `overflow-y:auto|scroll` and `scrollHeight > clientHeight`) and do `scroller.scrollTop += delta`, instant, never smooth. Add a guard that resets stray `window.scrollY / documentElement.scrollTop / body.scrollTop` back to 0 when the shell is locked. (This was THE iPhone-only bug; desktop Chrome and emulation never reproduce it. Test on real hardware.)
2. **Re-measure continuously, do not trust one measurement.** One `requestAnimationFrame` loop while a ring step is on screen: read the target rect, rewrite ring/hole/card only when top/left/width/height changed by more than 0.5 px (include `documentElement.scrollTop`, the scroller's `scrollTop`, `innerWidth/innerHeight` in the change key). A still page = zero style writes. Pause on `document.hidden`. Also listen to `scroll` with `capture:true` (scroll events do not bubble, so a container scroll never reaches a window listener) and to `visualViewport` `resize`/`scroll`.
3. **Finish the scroll, then show the ring.** On the FIRST render of a step (arriving on a page, moving to the next step) keep the card and ring hidden, keep the dim up (and the catcher blocking), and reveal only when the target's rect has been steady for about 5 frames AND at least 280 ms AND its images have loaded, with a hard cap (1.5 s) so a slow image can never hang the tour. Then one extra re-place at +400 ms and +1000 ms.
4. **But a same-step re-render must NOT hide the ring.** If the target is animating on purpose (the user tapped a button and it slides/expands), keep the ring visible and let the follow loop + the ring's CSS transition glide it along. Hiding it makes the tour look broken. Rule: only the first render of a step waits; "soft" re-renders (target animates, user taps Fix, Skip then Keep going) just re-place.
5. **Give the user an escape hatch for a wrong ring**: a small quiet "Highlight looks off? Fix" link on ring steps (never on the invitation, the end card or text-only steps). It is a SOFT re-place (reset stray scroll, re-scroll within the scroller if needed, `place()`), the ring slides to the right spot. Plus a debug box (`?tourdebug=1` or a sessionStorage flag): target top/height, spot `--y`, `scrollY`, `documentElement.scrollTop`, scroller `scrollTop`, `innerHeight`, `visualViewport.offsetTop/height/pageTop`. One screenshot from the user's phone then tells you what is shifting.
6. **Anchor the card to the ring** so the eye does not travel: 12 px below the ring if it fits above the limit, else 12 px above it, else a fixed top/bottom/centre fallback. Limits = safe-area top + 12, bottom nav height (probe element with `env(safe-area-inset-*)`), and the top of any sticky pay/checkout bar - 10. Never cover the ring, the primary action, or the pay bar. Recompute on every place().
7. **The dim must be strong enough for a white card to stand out**: .58 alpha navy, not .34 (a "soft" light dim made the card blend into the page; contrast white card vs backdrop about 2:1 at .34, about 3.9:1 at .58). Firmer shadow on the card, a `1px` ring border. Blur only the closing step if you want a "now back to the real page" feel.
8. **The target must be a REAL, tappable thing the next step needs.** A step that rings the first card in a list can ring something that cannot continue the flow (a cafe with no partner cafe, the item already in the cart). Mark targets server-side (`data-tour="..."`) ONLY when they can continue the flow, and degrade to a text step ("None can join right now", Skip / Next) when nothing qualifies. No dead ends: Esc / Skip tour is always available, behind a "Skip the tour?" confirm so an accidental Esc never ends it.
9. **Tour state belongs to the ACCOUNT, not the tab.** The server decides (`done_at` timestamp on the profile, nullable, NO backfill so every existing user gets it once). Client `sessionStorage` keys (step, snooze, done) survive logout/login in the same tab, so a second account inherited the first one's "done" and saw nothing. Fix: the server puts a one-way per-account tag on the root element (`substr(hash_hmac('sha256', (string) auth()->id(), config('app.key')), 0, 12)`, never the raw id/email); the script compares it with the stored tag and wipes its keys on mismatch, before anything else.
10. **Duplicate routes for the same page break gates.** The app had two URLs for the cafe list (a public legacy one, which login redirected to, and the logged-in one the tour knew). The tour never showed after login. Collapse to ONE canonical set for signed-in users (twin URLs 302 to it, query string preserved, route names kept for old links, JSON/ajax requests not redirected). Grep for every place a login/redirect/landing points before you gate a feature on a route name.
11. **Fail open.** Any error removes every layer and leaves the page exactly as it was (`try/catch` around start and render, teardown). A broadcast/announcement pop-up or an install banner open: wait and start later, never stack on top of them.
12. **Never block checkout.** The checkout step is soft: no catcher, the user can always pay. Never on payment / processing / return pages (explicit page whitelist, GET only).

## Server side (Laravel, ~60 lines)
- Feature flag off by default (`MULTI_TOUR_ENABLED=false`, read with `config()` not `env()`; remember `config:cache`; never write the flag as `off`/`no` with `(bool) env()`, use true/false).
- `MultiTour::shouldRun()`: flag on, GET only, a page in the whitelist (route name => page key), customer WITH a profile row, and `done_at === null` OR replay. Replay = `?tour=replay` once, then a SESSION flag (`multi_tour_replay`) so later pages still run it; cleared by the done endpoint and by logout (`session()->invalidate()`).
- The Blade component renders NOTHING unless `shouldRun()`: root `<div id="tour" hidden data-page data-cart-count data-cart-cafes data-vendor-in-cart data-replay data-replay-session data-done-url data-list-url data-uid>`. The server only hands over facts already on the page.
- `POST /multi-tour/done` (throttle 10/min, 404 while the flag is off) sets `done_at` once. Done AND Skip both call it.
- All copy is static text in the JS, set with `textContent` (no HTML injection); targets come from a fixed selector list; nothing is read from the URL except the literal `replay` / `tourdebug`.
- Inline CSS in the component on purpose: the ring must not depend on an asset rebuild (hosts without npm).

## Step logic (derived from the page, not stored)
The step is DERIVED from page + cart facts the server put on the root, so a refresh or the back button never strands the tour; only a small step number sits in `sessionStorage` (`{s, v:1}`), cleared on done/skip. `pick()` returns the step for this page: list page with items in the cart = "pick a second cafe" (joinable cards only); menu with cart empty = "add a dish"; checkout with >= 2 cafes = soft closing step. Retry from the end card goes back to the list: with items in the cart it resumes at the right step, with an empty cart at step 1.

## Copy rules
One sentence per step, verb first ("Tap the green button"). Kicker "Step N of M" plus a progress bar (M thin bars). No "click". No button that duplicates a tap the user must do on the page (we removed "Show me cafes": the customer taps the real ringed button). Never use the words surcharge/penalty for money lines. Closing card: "You can ... any time. Replay this from Profile."

## Accessibility + mobile-native
`role=dialog aria-modal=false`, card title focused with `preventScroll`, `aria-describedby` on the target, Esc opens the skip confirm, `prefers-reduced-motion` removes the ring transition/pulse/card animation, `prefers-reduced-transparency` hides the blur, 44 px targets, hit area for Skip/Fix not under the notch, text >= 12.5 px. Keyboard open on a form: hide the card (`focusin` on inputs).

## Test checklist (do this on a REAL phone, not only desktop)
1. Fresh account, whole flow start to end, every tap real. 2. Replay from Profile with an account that already finished: must continue past step 1. 3. Retry with an EMPTY cart and with items. 4. Step where the target is off-screen (forces a scroll): ring must sit on the target, also after the toolbar collapses. 5. A target that animates (button that slides/expands): ring follows, never disappears. 6. Zero eligible targets: text step, Skip works. 7. Log in as a second never-toured account in the same tab: invitation shows. 8. Announcement pop-up open at login: tour waits. 9. 320 px wide and 390 x 844: card never covers the ring or the pay bar. 10. Flag off: no layers, no queries, no JS.
Automated tests only cover markup/strings and the server gate; they CANNOT see a ring that is 48 px off. The two real catches here (iPhone ring offset, wrong-page gate) were found by the owner on a phone.
